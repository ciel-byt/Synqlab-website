## 1. System Classification

**System Type:** Multi-Agent Autonomous Task System (Hybrid: Tool-Calling + Coordinator + Pipeline DAG)

**Description:**
SynqLab is a product-grade agentic AI platform for protein engineering and computational biology. Researchers describe goals in natural language; a coordinator agent ("Research Director") orchestrates specialist worker agents through multi-step pipelines (generate → fold → analyze → report). The system supports three autonomy levels (copilot, supervised, autonomous), extensible skills, visual pipeline building, batch processing, and per-session cost controls. It differentiates from competitors by offering true agent autonomy with sub-agent coordination — not just tool access through a GUI.

**Critical Failure Modes:**
1. **Fabricated scientific data** — Agent produces numerical claims (pLDDT scores, ΔΔG values, melting temperatures) not grounded in tool outputs, leading researchers to act on hallucinated results
2. **Runaway token spend** — Autonomous mode enters infinite loops or excessive tool-calling, consuming org budgets without producing useful output
3. **Incorrect tool selection** — Agent calls `analyze_stability` when user asked for `predict_structure`, or fails to delegate to specialist workers when coordinator mode is appropriate
4. **Silent data corruption** — Pipeline DAG executes nodes out of order or drops intermediate results, producing reports from incomplete data
5. **Mock/real confusion** — Researchers mistake simulated mock-tool outputs for real computational predictions, undermining research integrity

## 1b. Domain Context

> Researched by `gsd-domain-researcher`. Grounds the evaluation strategy in domain expert knowledge.

**Industry Vertical:** Computational Biology / Protein Engineering

**User Population:** PhD-level researchers and computational biologists at biotech companies. They use SynqLab as a research workbench — submitting protein sequences, running structure predictions, analyzing mutational stability, and generating automated reports. They are domain experts but not necessarily AI/ML experts.

**Stakes Level:** High

**Output Consequence:** Agent outputs directly inform experimental decisions — which protein variants to synthesize, which mutations to test in the wet lab, and which structural predictions to trust. Incorrect predictions waste expensive wet-lab resources (weeks of work, $10K+ per synthesis round). Hallucinated stability scores could lead to synthesizing unstable proteins.

### What Domain Experts Evaluate Against

| Dimension | Good (Expert Accepts) | Bad (Expert Flags) | Stakes | Source |
|-----------|----------------------|-------------------|--------|--------|
| **Structural prediction quality** | pLDDT > 70 for ordered regions, realistic backbone geometry, consistent with known homologs | pLDDT values reported without context, non-physical conformations accepted | High — determines if protein is worth synthesizing | AlphaFold/ESMFold literature |
| **Stability analysis accuracy** | ΔΔG within ±1 kcal/mol of experimental values for known mutations, clear destabilizing/stabilizing classification | Fabricated ΔΔG values, ignoring epistatic effects, treating computational ΔΔG as absolute truth | High — wrong stability call wastes synthesis resources | FoldX benchmarks |
| **Sequence design quality** | Designs respect known functional motifs, maintain hydrophobic core, avoid aggregation-prone patches | Random mutations in active sites, designs that violate basic biophysics, no diversity in generated variants | Critical — bad designs are expensive dead ends | ProteinMPNN/ProtGPT2 literature |
| **Literature search relevance** | Returns papers matching the specific protein family, method, and organism; recent and high-impact | Returns tangentially related papers, misses landmark studies, cites retracted papers | Medium — time waste, potential misinformation | PubMed best practices |
| **Report completeness** | All tool results cited with units, confidence intervals noted, limitations acknowledged | Cherry-picked metrics, missing negative results, presenting mock data as real | High — reports are decision documents | Scientific reporting standards |

### Known Failure Modes in This Domain

1. **pLDDT overconfidence** — AlphaFold/ESMFold produce high pLDDT for intrinsically disordered regions when modeled as fragments rather than in full-protein context
2. **ΔΔG sign errors** — FoldX conventions for stabilizing/destabilizing mutations are counter-intuitive; agents may invert the interpretation
3. **Hallucinated experimental data** — LLMs trained on scientific literature may generate plausible-looking but fabricated experimental results when asked about specific proteins
4. **Sequence design mode collapse** — ProtGPT2 may generate sequences that are all minor variants of the same design, providing false confidence in diversity
5. **Batch result contamination** — When processing multiple sequences in parallel, results from one pipeline run may be incorrectly attributed to another sequence

### Regulatory / Compliance Context

- No direct FDA/EMA regulatory requirements for computational predictions (they are not diagnostic or therapeutic devices)
- Institutional biosafety requirements may apply if designed sequences are intended for synthesis (dual-use research of concern — DURC screening)
- Data handling: protein sequences may be proprietary trade secrets; agent sessions must maintain org-level isolation
- Audit trails recommended for GLP (Good Laboratory Practice) compliance when computational predictions inform experimental decisions

### Domain Expert Roles for Evaluation

| Role | Responsibility |
|------|---------------|
| Senior Computational Biologist | Reference dataset labeling — expected tool selections and output quality for 20 representative prompts |
| Structural Biologist | Rubric calibration — define pass/fail criteria for pLDDT interpretation and structural quality |
| Protein Engineer | Production sampling — weekly review of 10 randomly sampled agent reports for factual accuracy |
| ML/AI Engineer | LLM judge calibration — validate that code-based metrics correlate with expert assessments |

## 2. Framework Decision

**Selected Framework:** Custom (OpenAI Chat Completions API + Pydantic tool system)

**Version:** OpenAI API v1.x (`openai>=1.0`), Python 3.12+

**Rationale:**
SynqLab's agent system was built on a custom framework inspired by Claude Code's architecture (QueryEngine → AgentEngine, buildTool → build_tool). This was the right choice because:
1. **Full control over the agent loop** — the coordinator/worker pattern requires precise control over tool dispatch, sub-agent spawning, and budget enforcement that no off-the-shelf framework provides out-of-box
2. **Pydantic-native tool validation** — the scientific tools require strict input schemas that integrate tightly with the existing FastAPI backend
3. **Minimal abstraction overhead** — for a multi-agent system with 14 tools, 3 autonomy modes, and pipeline DAG execution, adding LangChain/LangGraph would be abstraction on top of abstraction
4. **Already built and tested** — 84 tests passing, Docker builds clean, engine is production-ready

**Alternatives Considered:**

| Framework | Ruled Out Because |
|-----------|------------------|
| LangGraph | Adds graph-based state management on top of our already-working coordinator/worker pattern; the checkpointing benefits don't justify the migration cost for a system already in production |
| OpenAI Agents SDK | Too opinionated about agent lifecycle; our custom coordinator/sub-agent pattern doesn't map cleanly to their Handoffs abstraction |
| CrewAI | Good for rapid prototyping but lacks fine-grained control over tool dispatch ordering and budget enforcement needed for scientific workflows |
| LlamaIndex | Data/RAG-first framework; our system is agent-first with tool-calling as the primary interaction pattern |

**Vendor Lock-In Accepted:** Partial — OpenAI model dependency via Chat Completions API. The `AgentEngine._call_llm()` abstraction makes model swapping straightforward (change `DEFAULT_MODEL`), but function-calling schema format is OpenAI-specific.

### Key Abstractions

| Concept | What It Is | When You Use It |
|---------|-----------|-----------------|
| `AgentEngine` | Core LLM query loop with OpenAI function calling | Every agent session — owns the message history and tool dispatch |
| `AgentTool` + `build_tool()` | Pydantic-based tool type system with input validation | Defining new scientific tools with typed schemas |
| `AgentContext` | Session-scoped state isolation (tool registry, skills, approvals) | Multi-user concurrent sessions |
| `BudgetTracker` | Per-session token/cost enforcement with soft/hard limits | Preventing runaway autonomous sessions |
| `PipelineEngine` | DAG-based execution of tool chains with topological ordering | Multi-step research workflows (generate → fold → analyze) |
| `BatchProcessor` | Fan-out CSV/FASTA inputs through pipeline definitions | Processing multiple sequences in parallel |
| `AutonomyMode` | Three-tier control: copilot/supervised/autonomous | Configuring researcher comfort level |

### Common Pitfalls
1. **Bare JSX returns in frontend components** — Vite 8's Rolldown parser requires parenthesized multi-line JSX (`return (<div>)` not `return <div>`)
2. **Case-sensitive imports** — Linux Docker builds fail on PascalCase component filenames; always use lowercase for `components/ui/`
3. **ToolResult API** — Use `result.is_success` and `result.error_message`, NOT `.ok` or `.error` (property naming follows the ToolResult dataclass)
4. **Missing `Float` import** — SQLAlchemy models that use Float columns must explicitly import it
5. **Mock mode default** — `SYNQLAB_MOCK_TOOLS` defaults to `"true"` — all tools return simulated data unless explicitly set to `"false"`

## 4. Implementation Guidance

**Model Configuration:**
- Primary: `gpt-4o` (128K context, function calling, $2.50/1M input, $10/1M output)
- Budget-conscious: `gpt-4o-mini` (128K context, $0.15/1M input, $0.60/1M output) — suitable for worker agents
- Temperature: 0.1 (low variance for scientific accuracy)
- Max turns: 25 (hard limit prevents runaway loops)

**Core Pattern:**
Stateless engine per conversation — all persistence happens in the API layer (FastAPI routes write to PostgreSQL). The engine yields `AgentEvent` objects via async generator, consumed by WebSocket handlers for real-time streaming to the React frontend.

**Tool Use:**
14 tools registered via `build_tool()` factory. Each tool has a Pydantic input schema, an async `call()` method, and optional `mock_mode` for simulation. Tools are partitioned: science tools (7) for workers, coordinator tools (4) for Research Director, skill tools (2) for all agents.

**State Management:**
- Session state: `AgentContext` (in-memory per session, DB-backed via `agent_sessions` table)
- Tool approvals: `context.wait_for_approval()` for copilot mode
- Budget: `BudgetTracker` tracks per-model token usage within the engine
- Skills: loaded from filesystem, injected as system prompt extensions

**Context Window Strategy:**
- 128K context with `gpt-4o` handles most research sessions
- Tool results are serialized as JSON in tool messages (compact)
- No explicit summarization/compaction yet — flagged for Milestone 2
- Pipeline results are streamed per-node, not accumulated

## 4b. AI Systems Best Practices

### Structured Outputs with Pydantic

All tool inputs are validated via Pydantic v2 schemas before execution:

```python
from pydantic import BaseModel, Field

class ProteinFoldingInput(BaseModel):
    sequence: str = Field(..., min_length=10, description="Amino acid sequence")
    model_name: str = Field(default="omegafold", description="Folding model to use")

tool = build_tool(
    name="predict_structure",
    description="Predict 3D structure from amino acid sequence",
    input_schema=ProteinFoldingInput,
    handler=fold_handler,
)
```

Validation failures return `ToolResult.fail()` with descriptive error messages — the LLM can self-correct on retry.

### Async-First Design

The engine is fully async (`async for event in engine.submit_message()`). Tool handlers are `async def`. The one common mistake: blocking I/O in tool handlers (e.g., synchronous HTTP calls to compute backends) — always use `httpx.AsyncClient` or `asyncio.to_thread()`.

### Prompt Engineering Discipline

- **System prompts** are agent-type-specific (6 profiles: general, protein_designer, research_director, folding_worker, stability_worker, sequence_worker, general_worker)
- **Skills** extend the system prompt at runtime via `skill.to_system_prompt_extension()`
- **Token budget**: system prompt is ~200-400 tokens per agent type; tools add ~100 tokens each to the schema

### Context Window Management

- Current strategy: full conversation history + tool results in context
- Risk: long sessions (>20 turns) may approach 128K limit
- Mitigation: `max_turns=25` hard limit, budget tracker as secondary gate
- Future: conversation summarization for sessions exceeding 80K tokens

### Cost and Latency Budget

- Per-session cost estimate: $0.05–$0.50 depending on tool count and model
- Latency tracking: `engine.latency_summary` provides per-call stats (R7)
- Threshold alerts: `SYNQLAB_LLM_LATENCY_WARN=30.0s`, `SYNQLAB_TOOL_LATENCY_WARN=60.0s`
- Model routing: coordinator uses `gpt-4o`, workers can use `gpt-4o-mini` for cost savings

## 5. Evaluation Strategy

### Dimensions

| Dimension | Rubric (Pass/Fail or 1-5) | Measurement Approach | Priority |
|-----------|--------------------------|---------------------|----------|
| **Tool selection correctness** | Pass: correct tool called for prompt. Fail: wrong tool or unnecessary tool call | Code-based — F1 score against 20-prompt reference dataset (`evals/eval_tool_selection.py`) | Critical |
| **Numerical claim grounding** | Pass: all numbers in response traceable to tool outputs. Fail: any fabricated number | Code-based — `guardrails.check_numerical_claims()` runs on every response | Critical |
| **Workflow completion** | Pass: all expected tools called, domain markers present. Fail: incomplete tool chain or missing output | Code-based — completion criteria scoring (`evals/eval_workflows.py`) | Critical |
| **Context faithfulness** | 1-5: ratio of grounded vs. ungrounded assertions (numerical + keyword overlap) | Code-based — `evals/eval_faithfulness.py` | High |
| **Mock disclaimer injection** | Pass: disclaimer present when `SYNQLAB_MOCK_TOOLS=true`. Fail: missing | Code-based — `guardrails.apply_mock_disclaimer()` | High |
| **Budget enforcement** | Pass: session stops at hard limit. Fail: exceeds budget | Code-based — 12 unit tests in `test_budget.py` | High |
| **Pipeline DAG correctness** | Pass: nodes execute in topological order, no dropped results. Fail: out-of-order or missing | Code-based — 10 unit tests + 5 integration tests | Medium |
| **Latency within thresholds** | Pass: LLM <30s, tool <60s. Fail: threshold exceeded | Code-based — `engine.latency_summary` + logger warnings | Medium |

## 6. Guardrails

### Online (Real-Time)

| Guardrail | Trigger | Intervention |
|-----------|---------|-------------|
| **Numerical claim check** | Response contains numbers not found in tool outputs | Flag — log warning, append ungrounded claim notice |
| **Mock disclaimer** | `SYNQLAB_MOCK_TOOLS=true` and response is final text | Block — append mandatory `⚠️ Simulated Results` disclaimer |
| **Budget hard limit** | Token usage exceeds `hard_limit` | Block — terminate session with `BUDGET_EXCEEDED` event |
| **Max turns limit** | Turn count exceeds `max_turns` (25) | Block — terminate loop, return partial results |
| **Tool validation** | Tool input fails Pydantic schema validation | Escalate — return error to LLM for self-correction |

### Offline (Flywheel)

| Metric | Sampling Strategy | Action on Degradation |
|--------|------------------|----------------------|
| Tool selection F1 | Weekly eval run against 20-prompt dataset | Investigate prompt changes if F1 drops below 0.85 |
| Faithfulness score | Sample 10 sessions/week for numerical + keyword scoring | Tighten guardrails or add domain-specific checks |
| Budget utilization | All sessions — aggregate cost per org per month | Alert if any org exceeds 80% of monthly quota |
| Latency p95 | All LLM calls — track via `engine.latency_summary` | Investigate if p95 exceeds 15s for LLM or 30s for tools |

## 7. Production Monitoring

**Tracing Tool:** Arize Phoenix (recommended — open-source, self-hostable, strong multi-agent tracing)

**Key Metrics to Track:**
1. **Tool selection accuracy** — % of tool calls matching expected tool for prompt category
2. **Numerical grounding rate** — % of responses with zero ungrounded claims
3. **Session completion rate** — % of sessions reaching `TURN_DONE` without `ERROR`
4. **Cost per session** — mean and p95 token spend, broken down by model
5. **Latency p95** — LLM call latency and tool execution latency

**Alert Thresholds:**
- Tool selection F1 < 0.80 → investigate model drift
- Ungrounded claim rate > 10% → tighten guardrails
- Session error rate > 5% → investigate API failures
- Cost p95 > $2.00/session → review budget limits
- LLM latency p95 > 20s → check OpenAI status / rate limits

**Smart Sampling Strategy:**
- **High-priority sampling:** Sessions with `BUDGET_WARNING` or `BUDGET_EXCEEDED` events (100% review)
- **Medium-priority:** Sessions using autonomous mode with >10 tool calls (50% review)
- **Low-priority:** Copilot sessions with <5 tool calls (10% random sample)
- **Signal-based:** Any session where the user re-submits a similar prompt within 2 minutes (retry signal)
