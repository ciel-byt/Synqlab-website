# Design Doc — Knowledge Store

## Summary

The Knowledge Store is SynqLab's fourth architectural layer. It provides a structured interface through which teams and projects inject prior knowledge into the system — labeled datasets, task configurations, domain notes, and cross-project findings — and through which downstream components (the reranker, the generator, and the agent) consume that knowledge at runtime.

The key property: **knowledge is versioned, scoped, and cumulative**. A brightness dataset uploaded by one lab today becomes part of the shared prior that improves the system for everyone working on GFP-related tasks tomorrow — with explicit attribution and project scoping.

---

## Problem / user story

**As a lab using SynqLab on a new GFP11 project**, I have:
- A dataset of 113 GFP11 sequences with experimental brightness labels
- A baseline GFP1-10 target sequence
- Informal knowledge from prior work ("positions 3 and 7 are sensitive to charged substitutions")

None of this currently has a home in SynqLab. The pipeline ignores it. When a new project starts, the system starts from scratch. When another team in the same lab works on a related task, they cannot benefit from what was learned.

**What we need:**
1. A way to register any of these as a named knowledge artifact
2. A way for the reranker, generator, and agent to automatically load and use relevant artifacts for the current task
3. A way for knowledge to persist and accumulate across rounds, projects, and teams — so the system gets smarter over time rather than resetting

---

## Non-goals

- **Not a general-purpose data lake.** The Knowledge Store is scoped to molecular design tasks. Raw sequencing files, lab protocols, and non-design data are out of scope.
- **Not a vector database (yet).** V1 uses structured storage and explicit tagging. Semantic retrieval (embedding-based lookup) is a V2 concern.
- **Not a training infrastructure.** The Knowledge Store provides data to training scripts; it does not run training itself.
- **Not a user-facing UI.** V1 exposes a Python API and CLI only.

---

## The four knowledge types

| Type | Description | Example |
|---|---|---|
| `dataset` | Tabular labeled data mapping sequences to measured properties | 113 GFP11 sequences + brightness scores |
| `target` | Definition of the design task: target molecule, assay, hit threshold | GFP1-10 sequence, τ = median fluorescence |
| `prompt` | Free-text or structured domain note injected into the agent's context | "Positions 3 and 7 are sensitive to charge" |
| `finding` | A structured result from a completed experiment, auto-generated by the system | "Round 3 top-k had avg iPTM 0.74 and 60% hit rate" |

All four are stored with the same envelope (see schema below), differing only in `kind` and `payload`.

## Proposed design

### Layer position

```
Teams / Projects
      │
      ▼
┌─────────────────────────────┐
│      Knowledge Store        │  ← new layer
│  register / retrieve / tag  │
└─────────┬───────────────────┘
          │ consumed by
    ┌─────┴──────────────────────────────┐
    │  Agent  │  Reranker  │  Generator  │
    └─────────────────────────────────────┘
```

### Scoping model

Every knowledge artifact belongs to a **scope**:

- `global` — available to all projects and teams (e.g. published GFP11 datasets)
- `team:<team_id>` — available to all projects within a team
- `project:<project_id>` — private to one project

When the system loads knowledge for a task, it merges artifacts in this priority order: `project` > `team` > `global`. More specific scope wins on conflict.

### Post-training path

This is the key mechanism for how SynqLab learns across projects over time:

```
Round N completes
      │
      ▼
All outcomes labeled → stored in Knowledge Store as `finding` (project scope)
      │
      ▼
Reranker retrained on project-scoped dataset + all team/global datasets
      │
      ▼
[optional] Finding promoted to team scope by team lead
      │
      ▼
[optional] Finding promoted to global scope (curated, anonymized)
      │
      ▼
Next project in same team starts with a pre-warmed reranker
```

**Post-training** here means: after each round, the system does a lightweight supervised update on the brightness model (or any task-specific metric model) using the full Knowledge Store corpus visible to that project — not just the data from the current round. As the global corpus grows, each new project benefits from all prior labeled data across all teams, without any team needing to share raw sequences (only anonymized score distributions are promoted to global scope).

### Ingestion interface

Three ways to register knowledge:

1. **File upload** — provide a path to a CSV/XLSX/FASTA + a schema descriptor
2. **Structured config** — provide a YAML/JSON artifact directly
3. **Auto-ingestion** — at the end of every round, the execution engine automatically writes a `finding` artifact from the run summary

All three produce the same internal representation.

## Interfaces / schemas

### Knowledge artifact envelope

```python
@dataclass
class KnowledgeArtifact:
    id: str                   # UUID, auto-generated
    kind: Literal["dataset", "target", "prompt", "finding"]
    scope: str                # "global" | "team:<id>" | "project:<id>"
    task_type: str            # e.g. "gfp11_brightness", "peptide_binding"
    name: str                 # human-readable label
    version: int              # incremented on update, never overwritten
    created_at: datetime
    created_by: str           # project/team/system
    payload: dict             # kind-specific (see below)
    tags: list[str]           # free-form, used for retrieval filtering
    provenance: dict          # links to source experiment/round if auto-generated
```

### Payload schemas by kind

**`dataset`**
```json
{
  "format": "csv" | "xlsx" | "fasta+labels",
  "path": "datasets/113setdiscrepantlabelswithpositives.xlsx",
  "columns": {
    "sequence": "GFP11_sequence",
    "label": "brightness",
    "split": "train" | "test" | null
  },
  "target_context": {
    "partner_sequence": "<GFP1-10 sequence>",
    "assay": "split_gfp_complementation"
  },
  "n_positive": 67,
  "n_negative": 46,
  "n_total": 113
}
```

**`target`**
```json
{
  "molecule": "GFP11",
  "partner": "GFP1-10",
  "partner_sequence": "MSKGEELFTGVVPILVELDGDVNGHKFSVSGEGEGDATYGKLTLKFICTTGKLPVPWPTLVTTLTYGVQCFSRYPDHMKQHDFFKSAMPEGYVQERTIFFKDDGNYKTRAEVKFEGDTLVNRIELKGIDFKEDGNILGHKLEYNYNSHNVYIMADKQKNGIKVNFKIRHNIEDGSVQLADHYQQNTPIGDGPVLLPDNHYLSTQSALSKDPNEKRDHMVLLEFVTAAGITLGMDELYK",
  "assay": "split_gfp_complementation",
  "hit_threshold_field": "brightness",
  "hit_threshold_value": null,
  "hit_threshold_strategy": "pilot_median"
}
```

**`prompt`**
```json
{
  "text": "Positions 3 and 7 of GFP11 are sensitive to charged substitutions. Avoid D/E/K/R at these positions.",
  "injection_point": "agent_system_prompt" | "reranker_feature_note" | "generator_constraint",
  "confidence": "high" | "medium" | "low"
}
```

**`finding`** (auto-generated)
```json
{
  "experiment_id": "exp-abc123",
  "round": 3,
  "n_candidates": 200,
  "n_hits": 28,
  "hit_rate": 0.14,
  "top_k_avg_iptm": 0.74,
  "top_k_sequences": ["RDHMVLL...", "..."],
  "reranker_version": "v3",
  "notes": ""
}
```

### Python API

```python
from synqlab.knowledge import KnowledgeStore

ks = KnowledgeStore(db_path="synqlab.db", artifacts_root="artifacts/knowledge/")

# Register the brightness dataset
ks.register(
    kind="dataset",
    name="GFP11 brightness — 113 discrepant labels with positives",
    scope="project:gfp11-v1",
    task_type="gfp11_brightness",
    payload={...},  # see dataset schema above
    tags=["gfp11", "brightness", "labeled", "113-set"]
)

# Register the target
ks.register(
    kind="target",
    name="GFP11 split-GFP complementation task",
    scope="team:synqlab-core",
    task_type="gfp11_brightness",
    payload={...}
)

# Retrieve all knowledge visible to a project (merges project + team + global)
artifacts = ks.retrieve(
    task_type="gfp11_brightness",
    project_id="gfp11-v1",
    team_id="synqlab-core",
    kinds=["dataset", "target", "prompt"]
)

# Promote a finding to team scope (done manually by team lead after review)
ks.promote(artifact_id="art-xyz", to_scope="team:synqlab-core")
```

### CLI

```bash
# Register a dataset from file
synqlab knowledge register \
  --kind dataset \
  --name "GFP11 brightness 113-set" \
  --scope project:gfp11-v1 \
  --task-type gfp11_brightness \
  --file datasets/113setdiscrepantlabelswithpositives.xlsx \
  --tag gfp11 --tag brightness

# List all knowledge artifacts for a project
synqlab knowledge list --project gfp11-v1

# Promote a finding to team scope
synqlab knowledge promote <artifact-id> --to team:synqlab-core
```

## How the reranker consumes the Knowledge Store

At training time, the reranker training script:

1. Calls `ks.retrieve(task_type, project_id, team_id, kinds=["dataset", "finding"])`
2. Loads all returned datasets and findings into a unified training frame
3. Deduplicates by sequence (exact match), keeping the most recent label on conflict
4. Trains on the merged corpus
5. Writes the trained model back as a `finding` artifact with provenance linking to all source artifacts used

This means: **as more teams upload their GFP11 brightness data, every subsequent reranker trained for any GFP11 project automatically benefits from the larger corpus** — with no manual data wrangling.

## How the agent consumes the Knowledge Store

At the start of each round, the agent:

1. Calls `ks.retrieve(kinds=["target", "prompt"])`
2. Injects `target` payloads into its task definition
3. Appends `prompt` payloads to its system prompt (filtered by `injection_point`)
4. Uses `target.hit_threshold_value` (or derives τ from the pilot dataset) to set the hit criterion

## Failure modes

| Failure | Impact | Mitigation |
|---|---|---|
| Dataset uploaded with wrong column names | Reranker training fails silently | Schema validation at registration time; reject with clear error |
| Two teams upload conflicting labels for the same sequence | Reranker gets contradictory signal | Log conflict; keep both with provenance; let reranker handle noise |
| Finding promoted to global scope with PII or sensitive sequences | Data leak | Promotion to global requires explicit review step; never auto-promote |
| Artifact path missing on disk but DB row exists | Retrieval returns empty payload | Artifact integrity check on `register`; re-register required on mismatch |

---

## Observability

- Every `register` and `retrieve` call is logged with artifact ID, scope, and caller
- Reranker training logs the list of artifact IDs used as training sources
- Corpus size (n_sequences, n_positive, n_negative) logged per training run
- Scope promotion events logged with actor, timestamp, and before/after scope

---

## Security / safety considerations

- `project` scope artifacts are never readable by other projects
- `team` scope artifacts are readable by all projects within the team only
- `global` scope requires explicit promotion — never automatic
- Sequences in `finding` artifacts promoted beyond `project` scope are hashed by default; raw sequences require opt-in
- No external API calls from the Knowledge Store; all I/O is local filesystem + SQLite in V1

## Rollout plan

| Phase | What ships |
|---|---|
| **V1 (now)** | `KnowledgeStore` class, `register` / `retrieve` API, dataset and target kinds, CLI, integration with reranker training script, registration of the 113-set brightness dataset |
| **V1.5** | `prompt` kind, agent injection of target + prompt artifacts, auto-ingestion of `finding` artifacts at round end |
| **V2** | Scope promotion workflow, cross-team corpus merging, corpus versioning, embedding-based semantic retrieval |
| **V3** | Multi-tenant API, org-level global corpus, anonymized sequence hashing for cross-org sharing |
